# GDS 仓库结构、计算效率与性能优化分析报告

分析日期：2026-09-11。依据本地 Git 快照、实际执行代码、既有运行日志、逐测线函数计时和 Windows 电源事件。此次仅编写报告与数据附件，没有修改算法、启动测试或推送 GitHub。

## 1. 结论与证据等级

1. **现有日志足以分析未完成测试。** 6进程测试有930条完整测线记录，另一轮12进程测试有1280条；还能读取一轮后来完成的2800条记录。未完成不等于没有可用函数计时。
2. **主要热点已由计时定位到悬空边提取函数。** 两轮未完成测试中，`get_ordered_red_segments_for_path` 的独占墙钟分别占94.625%和95.078%。该函数内逐候选边扫描整条父路径、用 `np.allclose` 找面索引，是静态代码确认的首要优化候选；但现有计时尚不能把函数内部的各个循环单独拆出比例。
3. **有序生长分组不是当前主要热点。** 用户记忆中的逆序种子、生长、标记已分组边确实存在；它发生在全部悬空边提取之后，不能消除前一步的面索引回查成本。
4. **不能把12进程的386.416分钟当作连续计算耗时。** B轮确实完成2800条，但中间包含约5小时32分钟系统睡眠；同时B、C两轮曾重叠运行。它不满足独占机器、连续运行的对外基准条件。
5. **当前计时入口的批次交接已不是首要矛盾；Git仓库原入口仍有批次屏障。** 必须区分“Git仓库的 main”与“本地测试所用自动入口”，避免拿一个入口的调度结构解释另一个入口的成绩。

### 2.2 两种入口的调度差别

- **Git仓库main：** 第792–814行设置15进程、每任务40条、每大批600条；大批循环内新建ProcessPoolExecutor，`executor.map`按提交顺序取结果。前面的慢任务可能阻挡后面结果的收集，大批结束后才进入下一大批。这份入口确有用户担心的批次屏障和反复建池。
- **实测自动入口：** 一个持久进程池，每任务10条，最多2×worker数个在途任务，按完成顺序取回并补交。12进程对应280个任务、最多24个在途任务。10条在同一工作进程内顺序执行；12个工作进程并行处理各自任务，完成一个任务即可接下一个，不等待整批12个全结束。
- 自动入口提取原脚本的函数/类声明执行，**不调用仓库main**；这也解释了为何几何方法相同而调度不同。

### 4.3 386分钟中的系统睡眠

B轮相邻资源采样的elapsed_s从2124.746跳到22023.054，间隔**19898.308秒（331.638分钟）**，而通常采样间隔约0.5秒。Windows System日志提供独立证据：

- Kernel-Power事件42：本地2026-09-11 00:50:27进入睡眠，原因记录为Application API。
- Power-Troubleshooter事件1：06:22:03记录从低功耗恢复；消息内睡眠UTC时间2026-09-10 16:50:25.695427400，唤醒UTC时间22:22:02.732722600，对应北京时间00:50:25至06:22:02。

23184.986−19898.308=**3286.678秒，约54.778分钟**。这是扣除一个采样长间隔的描述性参考，不是重新测得的连续运行成绩：间隔还包含边界采样开销，且剩余时间仍受到两轮重叠影响。CPU累计38880.422秒；按原墙钟平均仅1.677忙碌核，按上述非长间隔时间粗算约11.83核。低平均CPU不是进程池一直闲置的证据。

睡眠也会落入当时正在执行的函数计时：B轮路径拆分墙钟累计20017.368秒，却只用了118.484 CPU秒。因此其7.207%的墙钟占比不能理解为计算热点；CPU占比只有0.308%。不能把全局睡眠时长从每条测线随意扣除；没有函数起止时间戳，就不能精确重建每条被睡眠跨越的有效墙钟。

## 5. 未跑完也能分析：逐测线七阶段耗时

### 5.1 计时口径

每个完成任务的JSONL含 `task` 和 `functions`。functions已记录slice_key、函数、调用次数、含子调用墙钟、独占墙钟及含子调用进程CPU时间。这里按run_id和slice_key聚合，不要求最终的diagnostics文件存在。

- 单测线阶段占比 = 本阶段inclusive_seconds / 该测线process_single_slice.inclusive_seconds。
- 样本总体阶段占比 = 全部已完成测线本阶段耗时之和 / 全部已完成测线总耗时之和，**不是简单平均每条百分比**。
- 下表七个阶段按原run_all顺序互不嵌套，另有少量入口与监测余量。热点细分表使用exclusive_seconds避免父子函数重复相加。
- CPU列均为含子调用值；原监测器没有记录独占CPU，不伪造该字段。非常短函数可能受CPU计时粒度影响。
- 每条测线的函数时间不包括进程排队、任务初始化、写盘和结果交接；后三者有任务级记录，不能平均除以10后说成“每条实测写盘时间”。

### 6.1 内存与数据生命周期

2800条输入的lines_3d和face_ids数组共401,689,008字节（383.080MiB）；加载使主进程RSS增加411,803,648字节（392.727MiB）。它们最初在主进程字典里，不是Windows进程池自动共享的一块“内存池”。任务提交时需要序列化，工作进程会持有当前块的数据副本。

当前12进程入口会从主字典pop已提交输入；有界在途任务保留必要引用，任务完成后释放Future和payload。工作进程逐条计算、写入task文件、删除结果引用，每任务显式垃圾回收；父进程不再接收全部大型Python结果。已经切好的原始剖面本来就在slices.pkl中，不必为了释放其400MiB输入而再复制一份原始数据到盘。

| 内存观测 | B完整轮 | C中断轮 |
|---|---:|---:|
| 进程树峰值RSS | 1.663GiB | 1.657GiB |
| 进程树峰值私有提交 | 1.380GiB | 1.375GiB |

B轮12个worker首次任务前RSS约85.9–87.3MiB，最后任务后约95.9–103.9MiB，各任务结束采样最大约109.5–111.1MiB。没有观察到随2800条结果累计而增长到数GB/进程的趋势；这些是采样值，不能排除未采到的短暂峰值，也不等于正式内存泄漏证明。父进程仍保留轻量计时行，Python分配器也可能保留可复用页。

此前独立加载探针曾观察：NumPy和SciPy各启用24个OpenBLAS线程时单进程私有提交约1539.6MiB；限制每库1线程后约62.4MiB。这个探针结果来自上轮工作记录，此次未重跑；完整B轮的低提交峰值支持内存压力已显著缓解，但不能由此推导几何计算必然更快。RSS是驻留物理内存，私有提交是提交额度，`commit free`是剩余额度，不应混为已占用RAM。

## 7. 算法运行顺序与针对性优化

### 7.1 单剖面完整顺序

```text
交线段+face_ids+剖面坐标系
  → load_data：组织三维交线与面索引
  → extract_nodes：合并节点、统计连接数
  → segment_paths：图连通分量→独立子路径
  → compute_normals：路径排序/投影→法向信息（保存在results中）
  → extract_and_group_red_segments：
       非闭合子路径重新排序→投影/法向判别
       → 对每条悬空边回查face_idx→得到完整有序悬空边表
       → 倒序挑种子→向idx-1生长→标记已分组边→找下一个种子
  → correct_red_groups：逐组重做父路径排序和投影→截取校正节点
  → compute_2d_centroids：再次投影组节点→质心
  → 完整结果落盘→线面关联→三维体素与块体统计
```

用户记忆的生长优化存在于 `group_red_segments_by_connection_order`：`grouped_flags`避免重复入组，清理growth_points中的已分组候选，顺着相邻索引继续。它不是把原始父路径物理删除，也不是边找边省掉前面的face_idx回查。当前种子阈值40°，生长阈值代码为70°，注释仍写45°；识别法向y阈值−0.1。优化时先保持实际代码语义，不根据旧注释顺手改参数。BFS指广度优先搜索；本代码排序用BFS，连通分量拆分另用栈遍历。

### 7.2 优先级与实施边界

| 优先级 | 优化方向与代码位置（Git快照） | 为什么、复用什么 | 验证重点 |
|---|---|---|---|
| P0：基准可信度 | 独占一次进程池；记录休眠/暂停；报告同时保留总墙钟与有效观察时间 | 当前两轮重叠且一轮睡眠，不能提供可发表的连续耗时 | 同输入哈希、范围、输出终点、worker/库线程参数；避免拼接各轮最快分段 |
| P1：面索引查询 | `get_ordered_red_segments_for_path`第407–434行，尤其426–432行 | 每条悬空候选都遍历path_subset并allclose，最坏O(R×E)；在路径排序时传递原边身份及face_idx，或构建候选索引以缩小匹配范围 | 保持正反向匹配、原先首个命中、重复边/多face规则、容差语义；不得把函数95%直接说成此循环95% |

P1的细节尤其重要：现代码只传 `atol=tol_match`，没有把 `np.allclose` 的rtol显式置零。因此“端点保留6位小数后做精确字典查询”不能自动视作等价替换。优先传递确定的边身份；若要保留历史容差匹配行为，索引应返回候选并按原始顺序验证，不可默默改变face_idx首命中结果。另有 `_extract_ordered_edges` 辅助方法，但当前热点调用链未使用它，且其精确匹配规则需单独核对。

### 7.3 为什么只加进程很难回到10或20分钟

完整B轮单测线累计CPU约38498秒。假设工作量不变、12个worker各稳定使用一个核且完全均衡，仅按CPU累计量/12就约53.47分钟；这只是现有环境下的工作量数量级，不是跨机器理论下界。改为15个同等吞吐核也约42.78分钟。要明显提速，必须减少每条路径的重复查询和小数组操作，而非继续增加进程数。

在“其余成本不变、调度理想”的假设下，若95%的热点局部快5倍，Amdahl估算整体约4.17倍；快10倍约6.90倍。这只是优先级说明，**不是收益承诺**：当前尚无内部回查计时、等价替换实现或无干扰对照数据。

建议下一步先选同一份输入中的普通位置0.00m、10.00m及慢位置50.90m、51.80m，给热点内部三段补计时；保持同一worker/库线程配置，先做一个方向的结果等价比较，再决定是否全区测试。不要先做大重构、GPU迁移或扩大并行数。最终识别一致性要检查face_ids、分组边/方向、校正节点和线面输出，不能只看“数量还是2800”。
